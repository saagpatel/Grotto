# Grotto v1.7 — Streaming Adapter Input (Design)

Status: **design ratified, not yet implemented.** Resolves the one known scaling
limit of the v1.4 adapter mechanism — `collect.Run` buffering a stdout-consuming
adapter's entire stream in memory before parsing.

## Motivating evidence

`grotto run --adapter=go-test -- go test -json ./...` on a large repo can emit
100s of MB of `-json` to stdout. Today `collect.Run` captures **all** of it into a
`bytes.Buffer` (`marks.go:116`, `cmd.Stdout = &stdoutBuf`) and only walks it after
the process exits (`gotest.go` `ParseSpans` over `bc.Stdout`). Memory scales with
total test output, unbounded.

## Probe findings that shaped the design (verified by reading the v1.6 code)

1. **Cargo is not affected — it is a different *kind* of adapter.** `cargo`'s
   `CapturesStdout()` is `false`; it reads a *file path* off stderr and
   `os.ReadFile`s cargo's own HTML report (`cargo.go:305-311`). The big bytes live
   on disk, written and bounded by cargo. Streaming is meaningless for it. The
   memory problem is exclusive to `CapturesStdout()==true` stream-consuming
   adapters (go-test, future pytest/jest).
2. **We buffer bytes we then discard.** `applyEvent` (`gotest.go:126-138`) handles
   only `start/run/pass/fail/skip`. Every `"Action":"output"` event — every `t.Log`,
   every line a test prints — falls through and is **ignored**. Yet `Run` holds the
   entire stream, output events included, in RAM. On a verbose suite those discarded
   output events are the bulk of the bytes. Streaming consumes-and-discards each
   line; retained memory drops from "all of stdout" to "the span tree" — O(packages
   + tests), tiny.
3. **`os/exec` already owns the read goroutine.** Setting `cmd.Stdout` to an
   `io.Writer` makes `exec.Cmd` spawn an internal copy goroutine, joined by
   `cmd.Wait()` (inside `cmd.Run()`). A line-splitting writer therefore needs **no
   goroutine we own**, and every `Consume` call provably completes before
   `cmd.Run()` returns. No concurrency hazard, exit guaranteed.
4. **`spanBuilder` already separates fold from materialize.** `applyEvent` folds
   events into builders; `materialize` (which needs `endNs`) runs only at the end.
   Streaming maps onto this for free: fold during the run, materialize at Finalize.

## Ratified decisions

| Fork | Decision |
|------|----------|
| Memory-bounding strategy | **True streaming consume** — line-splitting `io.Writer` feeds `Consume` during the run; raw lines discarded immediately, only the span tree retained. (Rejected: spill-stdout-to-temp-file — minimal diff but merely relocates the discarded bytes to disk.) |
| How an adapter declares streaming | **Optional `StreamAdapter` interface** via type assertion (`ad.(StreamAdapter)`), idiomatic Go à la `io.WriterTo`/`http.Flusher`. cargo grows zero dead methods. (Rejected: a `Streaming() bool` flag that forces `Consume`/`Finalize` no-op stubs onto file-reader adapters.) |
| One parser, two drivers | go-test's parse core is shared: buffered `ParseSpans(bc)` becomes "seed a stream, feed it `bc.Stdout` line by line, `Finalize(bc.EndNs)`". The live path and the buffered/fallback path exercise the **same** state machine — no duplicated logic, `ParseSpans` stays the documented buffered entry point. |

## Architecture

### Adapter interfaces (`internal/adapter/adapter.go`)

`Adapter` is unchanged (cargo still satisfies it as-is). Add an optional richer
interface plus its seed/parser types:

```go
// StreamAdapter is an Adapter that consumes the child's stdout as a live stream,
// folding each line into span state as it arrives instead of buffering the whole
// stream and parsing after exit. Run drives it through a line-splitting writer, so
// the raw output is never accumulated — only the derived span tree is retained.
type StreamAdapter interface {
    Adapter
    // NewStream begins a streaming parse, seeded with the root identity and run
    // start. Called once, before the command runs.
    NewStream(init StreamInit) StreamParser
}

// StreamInit seeds a StreamParser with everything fixed before the run: the
// pre-generated root identity its spans parent under, the run-start anchor, and the
// span-ID factory (so ID generation stays centralized with collect).
type StreamInit struct {
    RootID    string
    TraceID   string
    StartNs   int64
    NewSpanID func() string
}

// StreamParser folds a live stdout stream into spans.
type StreamParser interface {
    // Consume folds one line of stdout into span state. Called inline from Run's
    // stdout pump (os/exec's copy goroutine); must not block.
    Consume(line []byte)
    // Finalize materializes the accumulated state into spans once the command has
    // exited and the run's end timestamp is known.
    Finalize(endNs int64) []model.Span
}
```

### go-test adapter (`internal/adapter/gotest.go`)

- Extract the existing event-folding state (the `pkgs`/`tests` maps + `handle`) into
  a `goTestStream` struct implementing `StreamParser`. `Consume(line)` is the body
  of the current per-line loop; `Finalize(endNs)` is `materialize`.
- `goTestAdapter` implements `StreamAdapter.NewStream` returning a fresh
  `goTestStream` seeded from `StreamInit`.
- `ParseSpans(bc)` is rewritten to drive the same stream over the buffer:
  `s := a.NewStream(...from bc...); for each line in bc.Stdout { s.Consume(line) }; return s.Finalize(bc.EndNs), nil`.
  One parser, both drivers — buffered path preserved for tests and as a fallback.

### `internal/collect` integration (`marks.go` Run)

- **Hoist ID generation.** Generate `traceID` + `rootID` *before* `cmd.Run()` and
  pass them into `assembleTrace` (signature gains `traceID, rootID string`;
  `assembleTrace` stops minting its own). `startNs` is already captured pre-run.
- **Wire the stream.** Three-way stdout decision, replacing the current two-way:
  - `ad.(StreamAdapter)` → `cmd.Stdout = newLineWriter(stream.Consume)` (no user
    passthrough — raw JSON; no RAM buffer). Seed `stream` from the hoisted IDs.
  - buffered + `CapturesStdout()` (none today) → current silent `stdoutBuf` path.
  - else (cargo / `ad==nil`) → current passthrough (+ stderr tee when `ad!=nil`).
- **Finalize after exit.** After `cmd.Run()` and `assembleTrace`: if streaming,
  `flush()` the line writer's trailing partial line, then graft
  `stream.Finalize(endNs)` under `rootID` (same graft block as today). The buffered
  `ParseSpans` path is unchanged for cargo.

### Line-splitting writer (`internal/collect`, small new type)

```go
// lineWriter is an io.Writer that calls onLine for each '\n'-terminated line and
// holds a trailing partial line until flush(). It never accumulates more than one
// line, bounding memory to a single event regardless of total stream size.
type lineWriter struct {
    buf    []byte
    onLine func(line []byte)
}
```

- `Write` appends, splits on `\n`, calls `onLine` per complete line, keeps the tail.
- `flush()` emits any trailing partial line after the process exits (defensive —
  `go test -json` newline-terminates every event, but a panic-truncated stream may
  not).

## Edge cases / failure modes

- **Pathological single line.** A test dumping a giant blob in one `output` event
  yields one enormous line, which `lineWriter` would accumulate whole. Real
  *structural* events (`start/pass/fail/skip`) are tiny; only `output` lines (which
  the parser discards) can be huge. Hardening: cap `buf` at a threshold (e.g. 1 MiB);
  on overflow before a newline, enter drop-until-next-`\n` mode and skip that line.
  Bounds per-line memory too, completing the "fully bounded" guarantee. Cut decision
  below.
- **Incomplete stream (panic/timeout).** Unchanged behavior: `materialize` fills
  missing bounds from `[StartNs, EndNs]`, so unterminated package/test spans still
  close at `endNs`. `flush()` ensures the final partial line is still offered.
- **Adapter that streams *and* has marks.** Independent channels (marks via socket,
  stream via stdout); stream spans graft under the same pre-generated `rootID` as
  the marks trace. No conflict.
- **Parse failure mid-stream.** A malformed line is skipped exactly as today
  (`json.Unmarshal` error → ignore line). Streaming cannot fail the run; a degenerate
  stream finalizes to whatever builders accumulated (possibly just the root).
- **`Finalize` returning zero spans.** Same as `ParseSpans` returning empty today —
  the graft block's `len(adSpans) > 0` guard already handles it; trace stores with
  just root + marks.

## v1.7 cut line

In scope: the `StreamAdapter`/`StreamParser` interfaces, `goTestStream`, the
`lineWriter`, the `Run` rewiring + `assembleTrace` ID hoist, go-test converted to
streaming with its buffered `ParseSpans` retained as the shared-core fallback.

Out of scope (note, don't build): a third adapter (pytest/jest) — separate release,
though this is the seam that makes it cheap; converting cargo (it has no stream).

**Per-line cap (1 MiB drop-mode):** recommend **in** — it's ~10 lines and closes the
last unbounded dimension, making the memory guarantee total rather than
"bounded-except-one-pathological-line". Final call at build kickoff.

## Verification plan

- Unit: `goTestStream` fed a canned `-json` byte slice line-by-line produces the
  same spans as today's `ParseSpans` over the same buffer (golden parity — proves
  the shared-core refactor is behavior-preserving).
- Unit: `lineWriter` — split across arbitrary `Write` chunk boundaries (a line split
  mid-event across two writes still emits once), trailing-no-newline flush, and the
  1-MiB drop-mode (if cut in).
- Unit: `assembleTrace` with injected `traceID/rootID` (deterministic IDs) — existing
  tests adjusted for the new signature.
- Integration/dogfood: `grotto run --adapter=go-test -- go test -json ./...` on this
  repo; confirm identical waterfall to v1.6, and (memory proof) that a synthetic
  high-`output`-volume run holds flat memory under streaming vs. buffered.
- Gates: `CGO_ENABLED=0 go build ./...` · `go test ./...` · `golangci-lint run ./...`
  · `/code-review` before merge · tagged release with static binaries + checksums.
